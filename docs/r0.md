# RISC Zero programs reference

- `hp-guest/`: the Hub's statement (`licash_hp::check`): the claim the
  holder's publication carries is owed at most the Hub's response `b′`. It
  commits Lichen's 68-byte journal `c ‖ H("licash/hp/word" ‖ Base digest)
  ‖ H(O_D ‖ checkpoint ‖ W)`, fixed when the contract opens, so the holder
  garbles for it before anyone proves.
- `chain-guest/`: the chain program (`licash_chain::extend`): one batch of
  the hub's header chain, which verifies the receipt of the batch before it.
  The statement of a contract of graph id 11 on reads Bitcoin through a
  receipt of it, not through every header ([The header chain](#the-header-chain)).
- `host/`: packs, executes and proves them. Every command also runs
  `licash_hp::check` (or `licash_chain::extend`) natively and fails when the
  guest disagrees with it.

Each is a workspace of its own. The guest reads the exit with
`crates/licash-statement` (what Bitcoin shows of it on Lichen's hub-proves
graph), a path dependency as `crates/licash-hp` and `crates/licash-chain` are.

## Prerequisites

[rzup](https://dev.risczero.com) with the `risc0` Rust toolchain (Rust
1.97), `cargo-risczero` and `r0vm` 3.1.x, and its RISC-V C toolchain (the
guests link libsecp256k1). `RISC0_TOOLCHAIN` and `RISC0_CC` override the default
paths, `~/.rustup/toolchains/risc0` and
`~/.risc0/cpp/bin/riscv32-unknown-elf-gcc`.

`r0/build-guest.sh` builds with the toolchains the kept programs were built
with alone, rzup's `rust` 1.97.0 (rustc `e638c6cfe`) and `cpp` 2024.1.5
(gcc 13.2.0), and the lockfiles as committed:

```sh
rzup install rust 1.97.0
rzup install cpp 2024.1.5
```

`LICASH_GUEST_ANY_TOOLCHAIN=1` builds with others, for a guest not to keep.

## Build

```sh
r0/build-guest.sh chain   # r0/guests/chain.{bin,id}
r0/build-guest.sh hp      # r0/guests/hp.{bin,id}
cargo build --release --manifest-path r0/host/Cargo.toml
```

The statement is built with the chain program's image id, kept in
`r0/hp-guest/chain.id`: build `chain` first, and `build-guest.sh chain` fails
unless the program it builds is that one (a new chain is a new id there, and a
new statement).

Builds are local and untracked in `r0/guests/`; image ids change with the
source. A build of a program to keep starts from an empty `/tmp/licash-r0/target`:
cargo's cache there is keyed by file times, which the copy preserves, so after
a rebase it can hand back the code of an earlier commit. A guest is built from a copy of its sources at `/tmp/licash-r0`,
whichever the checkout's directory (cargo hashes a path dependency outside
the guest's workspace by where it is), and cargo's directory is left out
of the paths it holds, so the same commit builds the same image id on any
machine. One build at a time uses that directory.

## Programs kept

Contracts open under the program `apps/contracts` names (`SIGNET` in
`apps/contracts/src/lib.rs`), which verifies receipts of the chain program it
names (`CHAIN`, also kept here, and the id in `r0/hp-guest/chain.id`). Those
opened under the ones before (`SIGNET_BEFORE`) are played still while this
build reads their Base. Each is kept in `r0/programs/` as `<image id>.bin`: a
contract opened under one is proven with it alone, so none is removed while
its contracts are played. A hub's prover lacking one responds to no contested
claim of its contracts (and alerts), so install every program before starting
an upgraded hub. Each file's image id is its name:

```sh
for p in r0/programs/*.bin; do
  cargo run -q --locked --release --manifest-path r0/host/Cargo.toml -- id "$p"
done
```

The note format v5 was a reset, as v4 and v3 were: no Base of an earlier
contract is read by this build (each embeds a keyset of the format before),
so `SIGNET_BEFORE` holds only the program of v5 before caps of any size,
and the statement programs of those contracts
(`ff8d5db8…` of note format v4, built from 57b3349d, and those before it)
are kept in `r0/programs/` up to the commit before this pin alone. They are
played by the release before, whose hub image holds them, until those

Measured with `licash-r0 hp-exec` (15 headers each): the benchmark's
answered input (`r0/host/bench.bin`, 27.3 kB) takes 50.7 M cycles (51.7 M
under `ff8d5db8…`, of its like of note format v4, 30.9 kB); the
statement's worst evidence, 32 settled notes each spent in a spend of 64
inputs and 128 outputs and cited by her signature alone (504 kB), 65.4 M
(67.4 M under `ff8d5db8…`), where cited whole it took about 5,800 M.

Mutinynet's contracts open under the same programs: the statement reads
the profile of the checkpoint it is given (Mutinynet retargets every 40,320
blocks), the Base's digest binds it, and a proof for one network is none
for the other. Its blocks come every 30 seconds, so a contract's headers
(and with them its proof's cycles) grow 20 times as quick in time: contracts
there are as long in blocks as signet's, not in time.

The program reads the sixth form of a Base only: her request's keys, the
notes she funded her contract with, and the script her default returns her
reserve to are always bound, and every lock's activation is anchored. It
reads each filing by its contract's graph id (`licash::recovery::Format`)
and checks each header once, on the zkVM's accelerator (9.4 k cycles a
header). A hub quotes a graph only where the program it trusts decides it
(`SIGNET_COMPACT`, `SIGNET_LEAN`, `SIGNET_CHAINED`, `SIGNET_OWN_CLAIMS`),
and holders refuse such a quote under any other.

The holder's and counter programs of the design before hub-proves are
gone with it: no contract opened under them is played.

Signet's are a trial under RISC Zero's shared Groth16 setup, and the
programs check signet's headers by their work alone, not by the network's
signature of each block: headers that fool them cost little to make.

The chain program is built from the commit its row names, not from the
newest: any edit to `crates/licash`, even one the chain never reads, builds it
to another image id (it links that crate), and a hub keeps one chain, so a
program whose sources did not change keeps its id and its file until
`licash-chain` or the zkVM's recursion does. A build of it from a later commit
fails `build-guest.sh`'s check against `r0/hp-guest/chain.id` for this reason:
that id is not to be updated for it, and the file kept is the one to use.

Rebuilt, a program's file may differ from the one kept in its symbols'
names, which its image id does not cover (they vary from build to build):
compare image ids, not files.

To name new ones, build them from a commit, rebuild them in another
checkout to see the same image ids, copy each `r0/guests/<name>.bin` to
`r0/programs/<image id>.bin`, and name them in `apps/contracts`, moving
the programs named before to `SIGNET_BEFORE` for the contracts opened
under them (none at a reset whose build reads no earlier Base).

A change of the format of notes, spends, Bases or the statement's input
without a new program fails `r0/host`'s tests: they execute the pinned
`SIGNET` program on `r0/host/bench.bin`, which must be as this library
writes it (export it again), and on each input the statement's tests
export from this checkout (`export_inputs`, `export_worst_inputs`,
`export_chained_inputs`, built by a nested `cargo test` of `regtest/`), and
fail if it panics reading one or decides one otherwise than the library.

## Execute and prove

A chained statement (graph id 11 on) verifies a receipt of the chain program, which
every command takes with `--assume <receipt>` (a succinct receipt, as
`chain-prove` leaves it in `<work-dir>/receipt`): the guest's execution makes
the assumption, and the proof resolves it, one recursion proof, before the Groth16
wrap, kept like each segment so a stopped proof carries on. A batch of the chain is
`licash_chain::Batch::to_bytes`; the statement's tests export both, the chain
in two batches and the answered claim on it:

```sh
LICASH_HP_INPUTS=$PWD/tmp/hp-inputs cargo test --release \
  --manifest-path regtest/Cargo.toml -p licash-hp export_chained_inputs
licash=r0/host/target/release/licash-r0
$licash chain-exec tmp/hp-inputs/batch-1.bin r0/guests/chain.bin
$licash chain-prove tmp/hp-inputs/batch-1.bin tmp/chain-1 r0/guests/chain.bin
$licash chain-prove tmp/hp-inputs/batch-2.bin tmp/chain-2 r0/guests/chain.bin \
  --assume tmp/chain-1/receipt
$licash hp-prove tmp/hp-inputs/answered-chained.bin tmp/dispute r0/guests/hp.bin \
  --assume tmp/chain-2/receipt
```

`chain-fake` makes a receipt of a batch's journal that proves nothing, for
`hp-exec --assume` to count a statement's cycles without proving the chain.

Export statement inputs (`licash_hp::HubInput::to_bytes`) from the
statement's tests: a 32-item claim the Hub answers with a 16-note spend,
and the same claim with a response it can't prove:

```sh
LICASH_HP_INPUTS=$PWD/tmp/hp-inputs cargo test --release \
  --manifest-path regtest/Cargo.toml -p licash-hp export_inputs
```

Then execute (journal and cycle count) or prove: a succinct receipt, its
Groth16 wrap, verified and exported to `<work-dir>/proof.json` as JSON with
the 256-byte seal that `lichen_babe::risc0::proof_from_seal` reads. The work
directory keeps the prover's progress (each segment proved), so a stopped
proof carries on where it was:

```sh
licash=r0/host/target/release/licash-r0
$licash hp-exec tmp/hp-inputs/answered.bin
$licash hp-prove tmp/hp-inputs/answered.bin tmp/answered
$licash probe
$licash bench tmp/bench.json
```

`probe` prints what the machine proves with (`cuda` or `cpu`, the programs
installed, its memory) and what it lacks, and with a program (`probe
<program>`, as the hub runs it) whether that program proves `bench.bin` as
this build's library does: a program built before a change of format is a
problem; `hp-reads <base.bin> [program]` executes a program on an input of a
Base (an exit of nothing, no evidence), and fails if it can't read it, as
the hub checks each opening's; `bench` proves two segments of
`r0/host/bench.bin` (the answered input), then wraps them, and prints the
seconds a segment takes and those of the wrap, as the hub plans its proofs
on. A program is a path, or an image id installed in
`$LICASH_R0_SHARE/programs/<id>.bin` (by default `../share/licash-r0` beside
the binary); RISC Zero's Groth16 setup is in its `groth16/` directory
(`stark_verify`, `stark_verify.dat`, `prover`, `stark_verify.cs`,
`stark_verify_final.pk.dmp`, from `risczero/risc0-groth16-prover`), x86-64
only. The hub's image (apps/hub/Dockerfile) installs both.

Built with `--features cuda` and installed beside it as `licash-r0-cuda`,
the CUDA build proves on the GPU: `licash-r0` uses it when
`licash-r0-cuda probe-gpu` finds a usable GPU, in segments of 2^18, then
2^17 should the GPU run out of memory (each attempt in a process of its
own), and proves on the CPU in segments of 2^19 otherwise. The Groth16 wrap
runs on the CPU either way. On an RTX 2060 (6 GB) the answered input proves
in about 20 minutes; on 6 CPU cores, about 8.5 hours.

`LICASH_SEGMENT_PO2` (13 to 20) sets the zkVM segment size.

The answered input (a 17 kB filing, 32 settled notes, a 16-note spend
cited by her signatures as evidence) executes in about 51 M cycles (53
segments of 2^20). Each
header of the exit adds about 9.4 k cycles in the newest program (3,000
more headers, 98 M cycles), 28 k in those before (157 M). Cycles grow
with the signatures and DLEQ proofs a filing carries, so a filing at the
64 kB limit is roughly three times that. Evidence costs what her claim
relies on, not the spends it cites: of graph id 14 on, the Hub cites a
spend by the signatures of her inputs alone, and its other inputs and
outputs cost only hashing its body (about 20 cycles a byte), so 32 notes
each cited from a spend of 64 inputs and 128 outputs take 65.4 M cycles,
where cited whole they took about 5,800 M. The Hub proves only when a holder
contests its response: it responds with less than the claim, the holder
checks the evidence it responded on (`licash_hp::bears_out`, the same test
as the statement's) and leaves a response that bears out alone, which then
pays what it says with no proof, and the Hub asserts the proof within the
graph's assert window of her contest otherwise.

A hub proves on signet through `licash-r0` (`LICASH_HP_PROVER` names
another), one proof at a time (docs/hub.md); no test plays a real
proof on Bitcoin yet.

## Setup trust

Groth16 needs a setup whose secret randomness must stay unknown: whoever
knew it could forge a proof the contract accepts, and cut a holder's payout
without her key. The STARK layer has no secret setup, and BABE's part is
agreed by wallet and hub when opening the contract. The shared key a trial
uses relies on at least one honest, erasing contributor in each of two
past ceremonies (Phase 1, the Powers of Tau Hermez selected: 54 of the
public Perpetual ceremony plus a beacon; Phase 2, RISC Zero's wrapper
circuit: 238 participants). They may be different people. Verify the
transcripts, a contribution hash and the resulting verification key against
the one the contract commits to; erasure cannot be shown.

A bilateral setup is a proposed option for new contracts, not built: wallet
and hub each contribute to both phases (Phase 2 alone leaves the Phase 1
assumption), each checks the result and the contract's commitment before
funding, and the hub keeps the proving key. The proof stays compact. The
cost falls on the holder's contribution: about 3 GiB of parameters at 2^23
for Phase 1, 3.45 GB and 25 minutes a participant for Phase 2 in RISC Zero's
ceremony, and a 32 GiB heap in its documented verification. Handing the hub
the seed defeats it. A public seed cannot replace the ceremony either:
Groth16 needs points (G, tG, t^2G) from one hidden scalar, and a public
seed lets anyone rebuild it. Setup and proof format:
[RISC Zero's setup guide](https://dev.risczero.com/api/trusted-setup-ceremony),
[ceremony security](https://eprint.iacr.org/2021/219).

checks), where the filing and evidence cost about 1.4 M cycles a note. A
contract of half a year (26 280 headers) adds about 190 M cycles to the
statement's 68 M: its age, not its claim, is then most of a proof, unless it
is chained (below).

## The header chain

A contract of graph id 11 on (`licash::recovery::chained`) is decided on a
receipt of the chain program, not on every header of its exit, so that a
dispute's cost does not grow with its age. The program (`r0/chain-guest`,
`crates/licash-chain`) proves the hub's headers in batches. Each batch
verifies the receipt of the one before, of the same program (`env::verify`,
by the image id the batch is given and its journal names, which the statement
checks is the one compiled into it), and appends a leaf to a Merkle tree for
each block: its height, its hash, the whole state a header is checked against
(`licash::chain::Checkpoint::commitment`: the last 11 times and the retarget
period's start, which the median and the retarget read) and the work since the
chain's start. The journal commits the tree's root, its frontier (so the next
batch extends that tree and no other), the last block's state and the work.

The statement (`licash_hp::headers`) verifies that receipt, opens the leaf at
its contract's checkpoint and requires the state it commits to be the one Base
binds, then reads the blocks of the exit and those the judgment of the claim
looks up through openings of their leaves (32 siblings each). The chain may
start anywhere, below the contract's checkpoint, for that is all it takes to
tie it to the contract: every later leaf is that state after a header
`Checkpoint::push` accepted, as a chain checked from the checkpoint would reach.
The work above the last block of the exit is the chain's after it and that of
a few headers the statement checks itself. A block the judgment looks up that
the input does not open is a statement the hub cannot prove
(`Refusal::Openings`), never a claim owed nothing, which `licash::recovery`
would otherwise make of an activation it cannot find. The hub finds the blocks
to open by running the judgment until it asks for none (`licash_hp::open_chain`).

Measured with `hp-exec` and `chain-exec` on the answered input (32 settled notes,
a 16-note spend as evidence, the lean filing):

| | cycles |
|---|---|
| dense statement, graph id 10, 15 headers | 45.2 M |
| the same with 3,015 headers | 68.8 M (7.9 k a header) |
| chained statement, any age (15 and 3,015 headers) | 45.5 M |
| a batch of the chain, 1,504 headers | 18.9 M (12.5 k a header) |
| `env::verify` of a receipt, in the guest | 7.5 k |

So a chained statement costs 0.3 M cycles more than the dense one of a new
contract (the openings and the receipt's journal) and no more at any age. At
signet's 26,280 headers a half year is 252 M cycles dense and 45.5 M chained, at
105,120 (two years) 873 M and 45.5 M. The chain costs 12.5 k cycles a header
once, in the background, for every contract on it: a day of signet's blocks is
1.8 M cycles, of Mutinynet's 36 M. Resolving the receipt is one recursion proof,
13 to 25 seconds on 12 CPU cores, 1 second on a GPU, as a join is.

Proven on an RTX 2060 (a shared machine, the Groth16 wrap included), a dispute on
a contract 3,015 blocks old took 17.2 minutes under the dense statement and 12.3
chained, which is what a contract of any age takes; a batch of 1,500 headers of the
chain took 4.5 minutes.

What the hub keeps and does about it is in docs/hub.md. A receipt of the chain
program resolves under the recursion circuit of the zkVM release that made it
(`risc0-zkvm` is pinned at 3.1.0): a release that changes it is a new chain, proven from
its start.

## The lean filing

A contract of graph id 10 on (`licash::recovery::Format::Lean`) files as the
compact one does and is judged item by item: the statement verifies the
issuance proof and hold signature of the items its input flags as invalid
(`HubInput::invalid`) and no others, and takes the rest as valid, which can
only raise what her claim is owed. The Hub finds the invalid items natively
(`licash_hp::flagged`) and a flag on a valid item is no proof; an invalid item
is worth nothing and the rest of the claim is owed, where under the compact
filing one voids it whole. The Hub reads her filing with the statement's own
decoding for all it does about her claim (`licash::recovery::named`: the
evidence it looks up, the notes it retires), never with the strict one a
wallet reads its own filing with: bytes the statement decides on and the Hub
refused left it answering nothing.

The statement verifies no hold signature of the inputs of a lock on its own
inputs (`Source::OwnInputs`) either, flagged or not: the refund of a lock the
Hub never certified is owed with a signature that is not its input's hold
key's. The Hub cannot answer that claim with less, so it retires the input by
the lock her filing shows, which its owner signed
(`licash::recovery::Named::locks`), and cites that lock, a spend, against any
other claim of the note. A statement that verified those signatures would
close it for the contracts opened under it; none of those open today does.

On the answered input:

| | compact | lean |
|---|---|---|
| her filing decoded and judged | 37.3 M | 19.1 M |
| total | 63.5 M | 45.3 M |

What is left is the evidence's decoding (25.9 M: every note and signature of
a spend the Hub cites) and, for each item, its hash to the curve. Signet and
Mutinynet contracts open under a program that decides it (`SIGNET_LEAN` in
`apps/contracts`).
